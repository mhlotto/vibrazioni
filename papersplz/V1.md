# papersplz v1 Specification

## 1. Purpose

`papersplz` is a local-first command-line tool for cataloging academic papers and related documents.

A catalog stores:

- copies of papers and documents
- bibliographic and descriptive metadata
- tags
- one review per paper
- zero or more comments per paper

The catalog must remain understandable and recoverable without `papersplz`. Metadata is stored as ordinary JSON files and the documents themselves are stored as ordinary files.

The initial implementation targets macOS, Linux, and FreeBSD.

## 2. Design principles

v1 should favor simple, durable behavior over abstraction or optimization.

- Use Go.
- Prefer the Go standard library.
- Do not require a database or server process.
- Use one JSON metadata record per paper.
- Keep catalogs self-contained and portable.
- Keep the stored document independent of the file from which it was imported.
- Treat human-readable CLI output and machine-readable JSON output as separate interfaces.
- Avoid unnecessary interfaces, frameworks, and package layers.
- Preserve room for future features without implementing them prematurely.

## 3. Non-goals for v1

v1 does not provide:

- PDF annotation
- PDF text extraction
- full-text search inside document contents
- DOI or arXiv metadata lookup
- citation graph management
- BibTeX import or export
- synchronization between machines
- shared or remote catalogs
- automatic webpage scraping
- a graphical interface

These may be added later without changing the basic catalog model.

## 4. Project and executable names

The project lives in:

```text
./papersplz/
```

The primary executable is:

```text
papersplz
```

A short executable name is also provided:

```text
pplz
```

`pplz` invokes the same program, normally via a symlink or equivalent packaging mechanism. There is only one implementation.

## 5. Catalog selection

Commands operate on one catalog.

Catalog resolution order is:

1. `--home PATH`
2. `PAPERSPLZ_HOME`
3. error

There is no implicit global default catalog in v1.

Examples:

```sh
export PAPERSPLZ_HOME="$HOME/papers/math"
pplz list

pplz --home "$HOME/papers/physics" list
```

If no catalog can be resolved, the command exits non-zero with an error explaining that `PAPERSPLZ_HOME` or `--home` is required.

`init` is exceptional because the target catalog path is supplied directly as an argument.

## 6. Catalog creation

```text
papersplz init PATH --name NAME [--description DESCRIPTION]
```

`init` must:

- create `PATH` if it does not exist
- refuse to overwrite an existing papersplz catalog
- refuse to silently adopt an unrelated non-empty directory
- create the required catalog structure
- record the catalog name
- record the optional description
- record the creation time
- record the schema version

Example:

```sh
pplz init ~/papers/math \
    --name "Mathematics" \
    --description "Mathematics papers and notes"
```

## 7. On-disk structure

A catalog uses this layout:

```text
CATALOG/
    catalog.json
    papers/
        PAPER_ID/
            record.json
            paper.pdf
        PAPER_ID/
            record.json
            paper.ps
```

The stored document filename is normalized to:

```text
paper.<extension>
```

The original filename is retained in metadata.

v1 does not require a generated search index.

## 8. Catalog metadata

`catalog.json` contains catalog-level metadata.

Example:

```json
{
  "schema_version": 1,
  "name": "Mathematics",
  "description": "Mathematics papers and notes",
  "created_at": "2026-08-24T15:30:00Z"
}
```

Times are stored in UTC using RFC 3339.

## 9. Paper identity

Each paper receives a stable generated ID when added.

The ID must:

- be unrelated to title or filename
- remain unchanged when metadata changes
- have enough entropy to make collisions negligible
- be safe for use as a directory name and CLI argument

A practical v1 representation is lowercase hexadecimal generated from cryptographically secure random bytes.

Commands may accept an unambiguous prefix of a paper ID.

Example:

```sh
pplz show a81f32
```

If a prefix matches no paper, the command fails.

If a prefix matches more than one paper, the command fails and reports the ambiguity.

## 10. Paper metadata

Each paper directory contains `record.json`.

Conceptual example:

```json
{
  "schema_version": 1,
  "id": "a81f32c991b7",
  "title": "Some Interesting Paper",
  "authors": [
    "Alice Smith",
    "Bob Jones"
  ],
  "source": "Journal of Interesting Things",
  "source_url": "https://example.org/paper.pdf",
  "added_at": "2026-08-24T15:31:00Z",
  "updated_at": "2026-08-24T15:31:00Z",
  "file": {
    "name": "paper.pdf",
    "original_name": "smith-interesting-paper.pdf",
    "size": 481231,
    "sha256": "..."
  },
  "tags": [
    "topology",
    "homotopy"
  ],
  "review": null,
  "comments": []
}
```

Only the following are required when adding a paper:

- title
- document

Authors, source, source URL, tags, review, and comments are optional.

## 11. Adding papers

```text
papersplz add SOURCE --title TITLE [options]
```

`SOURCE` may be:

- a local file
- a direct `http://` URL
- a direct `https://` URL

Examples:

```sh
pplz add ~/Downloads/paper.pdf \
    --title "Some Interesting Paper"
```

```sh
pplz add https://example.org/paper.pdf \
    --title "Some Interesting Paper"
```

Optional metadata:

```text
--author NAME
--source TEXT
--tag TAG
```

`--author` and `--tag` may be repeated.

When adding a local file, the file is copied into the catalog. The catalog must not depend on the original file continuing to exist.

When adding a URL, v1 downloads the supplied URL directly. It does not parse or scrape an HTML page to discover a paper.

For URL imports, the supplied URL is recorded as `source_url`.

The stored file extension should be derived conservatively from the original filename or URL path. If no usable extension is available, the document may be stored as `paper.bin`.

## 12. Duplicate detection

A SHA-256 digest is calculated while importing every document.

If an existing paper contains the same SHA-256 digest, `add` refuses the duplicate by default and identifies the matching paper.

v1 does not provide a duplicate override unless an actual use case requires one.

## 13. Removing papers

```text
papersplz remove PAPER
```

Removing a paper deletes its entire catalog-owned paper directory, including:

- stored document
- metadata
- review
- comments
- tags

The source file originally imported from the local filesystem is never modified.

Interactive use should prompt for confirmation.

Non-interactive deletion requires:

```text
--yes
```

v1 does not provide trash, restore, or `--keep-file` behavior.

## 14. Showing paper metadata

```text
papersplz show PAPER
```

The default human-readable output includes at least:

- ID
- title
- authors
- source
- source URL
- tags
- date added
- date updated
- stored filename
- original filename
- file size
- review status
- comment count

The default output does not need to print the full review or all comments.

## 15. Paper path

```text
papersplz path PAPER
```

This prints only the filesystem path to the stored document on stdout.

Examples:

```sh
open "$(pplz path a81f32)"
```

```sh
xdg-open "$(pplz path a81f32)"
```

`papersplz` does not need an `open` command in v1.

## 16. Listing papers

```text
papersplz list
```

Default output is concise and human-readable, for example:

```text
ID          TITLE                            AUTHORS
a81f32c9    Some Interesting Paper           Alice Smith, Bob Jones
410cbe13    Another Paper                    Carol Example
```

v1 supports useful filters that can be implemented without an index:

```text
--tag TAG
--author TEXT
```

Results should have a deterministic ordering. v1 should use title order unless a stronger reason emerges during implementation.

## 17. Reviews

A paper has zero or one review.

A review is intended to be a considered description of the paper, analogous in spirit to a Mathematical Reviews entry. It is distinct from working comments.

Commands:

```text
papersplz review show PAPER
papersplz review set PAPER TEXT
papersplz review edit PAPER
papersplz review remove PAPER
```

File input is supported:

```text
papersplz review set PAPER --file FILE
```

Stdin is supported with `-`:

```sh
cat review.txt | pplz review set a81f32 -
```

`review edit` opens `$EDITOR`.

If `$EDITOR` is unset, the command fails with a useful error rather than guessing an editor.

Conceptually a review contains:

```json
{
  "text": "...",
  "created_at": "2026-08-24T16:00:00Z",
  "updated_at": "2026-08-24T16:00:00Z"
}
```

Updating an existing review preserves `created_at` and changes `updated_at`.

## 18. Comments

Comments are working notes associated with a paper. They may contain questions, observations, links, reminders, or references to other resources.

Commands:

```text
papersplz comment add PAPER TEXT
papersplz comment list PAPER
papersplz comment show PAPER COMMENT
papersplz comment edit PAPER COMMENT
papersplz comment remove PAPER COMMENT
```

Each comment has:

- a stable generated comment ID
- text
- creation time
- modification time

Conceptually:

```json
{
  "id": "c91e84f2",
  "text": "How does Lemma 4 follow from the previous result?",
  "created_at": "2026-08-24T16:10:00Z",
  "updated_at": "2026-08-24T16:10:00Z"
}
```

Comments are ordered by creation time by default.

Comment IDs may use unambiguous prefixes within the containing paper.

## 19. Tags

Commands:

```text
papersplz tag add PAPER TAG...
papersplz tag remove PAPER TAG...
papersplz tag list PAPER
```

Tags are normalized to lowercase.

Leading and trailing whitespace is removed before validation.

Tags may not contain spaces.

The accepted v1 character set is:

```text
[a-z0-9][a-z0-9._+-]*
```

Examples of valid tags:

```text
algebraic-topology
to-read
p-adic
qft
category_theory
```

Duplicate tags on the same paper are not stored twice.

## 20. Search

```text
papersplz search TERM...
```

Search covers metadata managed by `papersplz`:

- title
- authors
- source
- tags
- review text
- comment text

Search does not inspect document contents in v1.

Search is:

- case-insensitive
- plain text
- not regular-expression based

Multiple terms use AND semantics. Terms may match across different fields of the same paper.

Example:

```sh
pplz search spectral sequence
```

A paper matches if both `spectral` and `sequence` occur somewhere in its searchable metadata.

Structured filters include:

```text
--tag TAG
--author TEXT
```

Examples:

```sh
pplz search --tag topology
pplz search serre --tag homotopy
```

A linear scan of `record.json` files is sufficient for v1.

## 21. Machine-readable output

Commands returning structured information should support:

```text
--json
```

At minimum:

- `list`
- `show`
- `search`
- `review show`
- `comment list`
- `comment show`
- `tag list`

Human-readable output remains the default.

JSON output is part of the CLI interface and must have tests. It should be generated from defined output structures rather than by parsing or reusing formatted terminal text.

## 22. Atomicity and durability

Metadata changes use atomic replacement where supported:

1. create a temporary file in the destination directory
2. write the complete new JSON
3. close the file successfully
4. rename it over the destination

A failed metadata write should not normally leave a truncated `record.json` or `catalog.json`.

Paper import should stage work so that an interrupted or failed import does not leave what appears to be a complete paper record.

Incomplete temporary files or directories should be cleaned up when practical.

## 23. Schema handling

Both catalog metadata and paper records include `schema_version`.

v1 uses:

```text
schema_version = 1
```

Before modifying a catalog or paper record, `papersplz` checks that the schema version is supported.

An unknown future schema version causes an error. The program must not silently rewrite data whose schema it does not understand.

## 24. Validation

Commands must reject a directory that does not appear to be a valid papersplz catalog.

Metadata decoding should reject structurally invalid required fields rather than silently repairing them during ordinary commands.

Validation helpers should be shared by commands and `doctor` where practical.

## 25. Doctor

```text
papersplz doctor
```

`doctor` checks catalog consistency without modifying the catalog.

At minimum it checks:

- valid `catalog.json`
- supported catalog schema version
- readable `papers/` directory
- valid paper records
- supported paper schema versions
- paper ID matches its directory name
- referenced stored document exists
- recorded file size matches the stored document
- recorded SHA-256 matches the stored document
- duplicate paper IDs
- duplicate content hashes
- malformed tags
- malformed comments or review metadata
- unexpected or obviously incomplete paper directories

`doctor` reports every problem it can safely discover rather than stopping after the first unrelated problem.

It exits zero when the catalog passes its checks and non-zero when problems are found.

## 26. Output and exit behavior

General Unix conventions apply.

```text
0         success
non-zero  failure
```

Errors and diagnostics go to stderr.

Normal command results go to stdout.

Commands intended for scripting, such as `path` and JSON output modes, must avoid decorative or explanatory text on stdout.

## 27. Initial source layout

A reasonable starting layout is:

```text
papersplz/
    cmd/
        papersplz/
            main.go
    internal/
        cli/
        catalog/
        model/
        store/
        search/
    go.mod
    README.md
    Makefile
```

This layout is guidance rather than a requirement. Packages should exist because they encapsulate real responsibilities, not merely to create architectural layers.

The CLI parser may use the Go standard library, including `flag.FlagSet`. v1 does not require Cobra or another CLI framework.

## 28. Testing expectations

v1 should have automated tests for at least:

- catalog initialization
- refusal to overwrite an existing catalog
- catalog discovery via `--home`
- catalog discovery via `PAPERSPLZ_HOME`
- local file add
- URL download add
- document copying
- SHA-256 recording
- duplicate detection
- paper ID prefix resolution
- ambiguous prefix handling
- paper removal
- tag normalization and validation
- review set/show/edit/remove behavior
- comment add/list/show/edit/remove behavior
- search across each searchable metadata field
- AND semantics for multiple search terms
- structured tag and author filters
- JSON output
- malformed metadata handling
- unknown schema version handling
- atomic metadata updates
- `doctor`

Integration tests may execute the CLI against temporary directories.

Tests must not depend on the user's real home directory, environment, editor configuration, or network access unless the test explicitly creates a controlled local substitute.

## 29. v1 completion criteria

v1 is complete when a user can:

1. create a catalog
2. add local or directly downloadable papers
3. list and inspect papers
4. locate the stored document
5. remove papers safely
6. maintain one review per paper
7. maintain comments per paper
8. add and remove tags
9. search catalog metadata and notes
10. consume supported results as JSON
11. verify catalog integrity with `doctor`
12. move or copy the entire catalog to another supported system and continue using it by setting `PAPERSPLZ_HOME` or `--home`

Features outside these criteria belong to later milestones unless they are required to make the v1 implementation correct or maintainable.
